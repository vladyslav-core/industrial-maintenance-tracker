# 03 — Модель данных и бизнес-правила

## 1. Назначение документа

Этот документ фиксирует логическую модель данных и бизнес-правила MVP приложения **Industrial Maintenance Tracker**.

На этом этапе определяются:

- основные сущности приложения;
- поля каждой сущности;
- обязательные и необязательные данные;
- связи и кардинальности;
- роли пользователей;
- статусы оборудования и заявок;
- приоритеты заявок;
- разрешённые действия каждой роли;
- жизненный цикл ремонтной заявки;
- правила создания записи в истории технического обслуживания;
- проверки целостности данных;
- пограничные и ошибочные ситуации.

Документ не описывает Java-классы, JPA-аннотации, таблицы PostgreSQL, SQL-миграции, Spring Boot-конфигурацию и конкретную программную реализацию. Техническая реализация должна позже опираться на правила этого документа.

---

## 2. Основные сущности

В MVP используются четыре основные сущности:

1. `User`;
2. `Equipment`;
3. `RepairRequest`;
4. `MaintenanceRecord`.

### 2.1. User

Представляет зарегистрированного пользователя приложения.

Отдельные сущности `Admin`, `Technician` и `Requester` не создаются. Все они являются пользователями, а полномочия определяются полем `role`.

### 2.2. Equipment

Представляет конкретную физическую единицу оборудования: станок, насос, компрессор, двигатель, конвейер или другой технический объект.

Одна запись `Equipment` соответствует одной физической единице оборудования, а не общему типу или модели.

### 2.3. RepairRequest

Представляет неисправность и процесс её обработки.

Заявка хранит:

- какое оборудование неисправно;
- кто сообщил о проблеме;
- описание проблемы;
- срочность;
- текущего исполнителя;
- этап ремонта;
- результат работы;
- даты основных событий.

### 2.4. MaintenanceRecord

Представляет подтверждённый факт выполненного ремонта.

```text
RepairRequest
= проблема и процесс её обработки

MaintenanceRecord
= окончательно зафиксированный результат ремонта
```

## 3. Перечисления

Для MVP используются четыре перечисления.

### 3.1. UserRole

```text
ADMIN
TECHNICIAN
REQUESTER
```

#### ADMIN

Отвечает за:

- создание и управление пользователями;
- создание и изменение оборудования;
- изменение приоритета;
- назначение и переназначение техника;
- отмену назначенных заявок;
- возврат выполненной заявки в работу;
- окончательное закрытие заявки.

В текущем MVP `ADMIN`:

- не назначается исполнителем;
- не начинает ремонт;
- не заполняет `resolution`;
- не переводит заявку в `COMPLETED`.

#### TECHNICIAN

Может:

- создавать заявки;
- просматривать назначенные ему заявки;
- начинать работу по назначенной заявке;
- заполнять результат ремонта;
- переводить заявку в `COMPLETED`;
- просматривать историю оборудования.

#### REQUESTER

Может:

- просматривать оборудование;
- создавать заявки;
- редактировать собственную новую заявку до назначения;
- отменять собственную заявку в статусе `NEW`;
- отслеживать собственные заявки;
- просматривать историю оборудования.

#### Правила ролей

1. У пользователя одна обязательная роль.
2. Несколько ролей одновременно не поддерживаются.
3. Роль изменяет только `ADMIN`.
4. Исполнителем может быть только пользователь с ролью `TECHNICIAN`.
5. Пользователь с ролью `ADMIN` не считается техником.
6. Роль техника нельзя изменить, пока за ним закреплены незавершённые заявки.
7. Нельзя изменить роль последнего активного администратора.

### 3.2. EquipmentStatus

```text
OPERATIONAL
UNDER_REPAIR
OUT_OF_SERVICE
DECOMMISSIONED
```

- `OPERATIONAL` — оборудование доступно для эксплуатации.
- `UNDER_REPAIR` — оборудование временно ремонтируется.
- `OUT_OF_SERVICE` — оборудование временно выведено из эксплуатации.
- `DECOMMISSIONED` — оборудование окончательно списано.

Допустимые переходы:

```text
OPERATIONAL → UNDER_REPAIR
OPERATIONAL → OUT_OF_SERVICE
OPERATIONAL → DECOMMISSIONED

UNDER_REPAIR → OPERATIONAL
UNDER_REPAIR → OUT_OF_SERVICE
UNDER_REPAIR → DECOMMISSIONED

OUT_OF_SERVICE → OPERATIONAL
OUT_OF_SERVICE → UNDER_REPAIR
OUT_OF_SERVICE → DECOMMISSIONED
```

`DECOMMISSIONED` является окончательным состоянием в MVP.

Статус оборудования изменяет только `ADMIN`. Статус заявки не меняет статус оборудования автоматически.

### 3.3. RepairRequestStatus

```text
NEW
ASSIGNED
IN_PROGRESS
COMPLETED
CLOSED
CANCELLED
```

- `NEW` — заявка создана, техник не назначен.
- `ASSIGNED` — техник назначен, работа не начата.
- `IN_PROGRESS` — ремонт выполняется.
- `COMPLETED` — техник закончил работу и передал результат на проверку.
- `CLOSED` — администратор принял результат; создана история обслуживания.
- `CANCELLED` — заявка завершена без подтверждённого ремонта.

### 3.4. RepairRequestPriority

```text
LOW
MEDIUM
HIGH
CRITICAL
```

- `LOW` — незначительная проблема.
- `MEDIUM` — обычная неисправность; значение по умолчанию.
- `HIGH` — серьёзная неисправность, требующая быстрого вмешательства.
- `CRITICAL` — аварийная или потенциально опасная ситуация.

При непосредственной опасности сотрудник сначала выполняет реальные аварийные процедуры предприятия, а затем регистрирует заявку.

## 4. Сущность User

### 4.1. Поля

| Поле | Обязательность | Назначение |
|---|---|---|
| `id` | обязательное | Уникальный внутренний идентификатор |
| `fullName` | обязательное | Полное имя |
| `email` | обязательное, уникальное | Логин |
| `passwordHash` | обязательное | Защищённый хеш пароля |
| `role` | обязательное | Роль |
| `active` | обязательное | Разрешён ли доступ |
| `createdAt` | обязательное | Дата создания |
| `updatedAt` | обязательное | Дата изменения |

### 4.2. Правила

#### id

Создаётся системой и не изменяется вручную.

#### fullName

- минимум 2 символа;
- максимум 100 символов;
- не состоит только из пробелов;
- допускает буквы разных алфавитов, дефисы и апострофы.

Для MVP имя не разделяется на `firstName` и `lastName`.

#### email

- корректный формат;
- максимум 254 символа;
- уникальность без учёта регистра;
- перед сохранением приводится к нижнему регистру.

`User@Example.com` и `user@example.com` считаются одинаковыми.

#### passwordHash

- обязателен для любого пользователя, включая деактивированного;
- не отображается;
- открытый пароль не хранится;
- минимальная длина исходного пароля — 8 символов.

#### active

При создании:

```text
active = true
```

Если `active = false`, пользователь не может войти и выполнять действия, но его старые связи сохраняются.

### 4.3. Создание и изменение

Самостоятельной регистрации нет.

Пользователя создаёт только `ADMIN`.

Только `ADMIN` может:

- изменить имя;
- изменить email;
- изменить роль;
- активировать;
- деактивировать.

Пользователь может изменить собственный пароль.

### 4.4. Удаление и ограничения

Физическое удаление не используется. Вместо него:

```text
active = false
```

Нельзя:

- деактивировать последнего активного `ADMIN`;
- изменить его роль;
- деактивировать `TECHNICIAN`, если у него есть заявки `ASSIGNED`, `IN_PROGRESS` или `COMPLETED`;
- изменить роль такого техника до обработки его заявок.

## 5. Сущность Equipment

### 5.1. Поля

| Поле | Обязательность | Назначение |
|---|---|---|
| `id` | обязательное | Уникальный идентификатор |
| `name` | обязательное | Название |
| `inventoryNumber` | обязательное, уникальное | Инвентарный номер |
| `description` | необязательное | Дополнительное описание |
| `location` | обязательное | Местоположение |
| `status` | обязательное | Эксплуатационное состояние |
| `createdAt` | обязательное | Дата создания |
| `updatedAt` | обязательное | Дата изменения |

### 5.2. Правила

#### name

- минимум 2 символа;
- максимум 120 символов;
- не обязано быть уникальным.

#### inventoryNumber

- минимум 2 символа;
- максимум 50 символов;
- уникален без учёта регистра;
- является основным бизнес-идентификатором.

`eq-001` и `EQ-001` считаются одинаковыми.

#### description

Необязательное, максимум 1000 символов.

Для MVP производитель, модель и серийный номер могут быть указаны здесь.

#### location

- минимум 2 символа;
- максимум 120 символов;
- хранится текстом.

Отдельная сущность `Location` не создаётся.

#### status

При создании по умолчанию:

```text
status = OPERATIONAL
```

### 5.3. Права и жизненный цикл

Создавать и изменять оборудование может только `ADMIN`.

Новые заявки разрешены для:

```text
OPERATIONAL
UNDER_REPAIR
OUT_OF_SERVICE
```

Для `DECOMMISSIONED` новые заявки запрещены.

Одно оборудование может иметь несколько открытых заявок, потому что неисправности могут быть разными.

### 5.4. Списание и удаление

Списание запрещено, если существуют заявки:

```text
NEW
ASSIGNED
IN_PROGRESS
COMPLETED
```

Физическое удаление допустимо только для ошибочно созданной карточки без заявок и без истории.

Во всех остальных случаях используется `DECOMMISSIONED`.

## 6. Сущность RepairRequest

### 6.1. Поля

| Поле | Обязательность | Назначение |
|---|---|---|
| `id` | обязательное | Уникальный идентификатор |
| `title` | обязательное | Краткое название проблемы |
| `description` | обязательное | Подробное описание |
| `equipment` | обязательное | Оборудование |
| `createdBy` | обязательное | Автор |
| `assignedTechnician` | необязательное до назначения | Текущий исполнитель |
| `priority` | обязательное | Срочность |
| `status` | обязательное | Этап обработки |
| `resolution` | условно обязательное | Результат ремонта |
| `cancellationReason` | условно обязательное | Причина отмены |
| `createdAt` | обязательное | Время создания |
| `updatedAt` | обязательное | Время изменения |
| `assignedAt` | необязательное | Время последнего назначения |
| `startedAt` | необязательное | Время первого начала работы |
| `completedAt` | необязательное | Время завершения работы техником |
| `closedAt` | необязательное | Время перехода в окончательный статус |

### 6.2. Правила полей

#### title

- минимум 5 символов;
- максимум 150 символов;
- кратко и конкретно описывает проблему.

#### description

- минимум 10 символов;
- максимум 3000 символов;
- описывает наблюдаемую неисправность.

#### equipment

- должно существовать;
- не должно быть `DECOMMISSIONED`;
- после создания заявки не заменяется.

Если оборудование выбрано неверно, заявка отменяется и создаётся новая.

#### createdBy

- устанавливается системой;
- не выбирается вручную;
- не изменяется.

Название `createdBy` используется потому, что заявку может создать пользователь любой роли.

#### assignedTechnician

- отсутствует в `NEW`;
- содержит только активного `TECHNICIAN`;
- одна заявка имеет не более одного текущего техника;
- история переназначений в MVP не хранится.

#### priority

Если значение не указано:

```text
priority = MEDIUM
```

Начальный приоритет выбирает автор.

После создания его изменяет только `ADMIN` в статусах:

```text
NEW
ASSIGNED
IN_PROGRESS
```

При выборе `CRITICAL` требуется подтверждение пользователя.

#### status

Начальное значение:

```text
status = NEW
```

Статус не изменяется через произвольный список. Используются отдельные действия: назначить, начать, завершить, вернуть, закрыть, отменить.

#### resolution

- не требуется при создании;
- заполняется только назначенным `TECHNICIAN`;
- редактируется в `IN_PROGRESS`;
- обязателен для `COMPLETED`;
- блокируется в `COMPLETED`;
- снова доступен после возврата в `IN_PROGRESS`;
- не изменяется после `CLOSED`.

Рекомендуемая структура:

1. Что обнаружено?
2. Что сделано?
3. Каков результат проверки?

#### cancellationReason

- обязателен для `CANCELLED`;
- минимум 5 символов;
- максимум 500 символов;
- содержит понятную причину.

#### временные поля

Даты устанавливает система.

Логический порядок:

```text
createdAt
≤ assignedAt
≤ startedAt
≤ completedAt
≤ closedAt
```

`closedAt` — время перехода в `CLOSED` или `CANCELLED`.

## 7. Жизненный цикл RepairRequest

### 7.1. Основной путь

```text
NEW
  ↓
ASSIGNED
  ↓
IN_PROGRESS
  ↓
COMPLETED
  ↓
CLOSED
```

### 7.2. Все разрешённые переходы

```text
NEW → ASSIGNED
NEW → CANCELLED

ASSIGNED → NEW
ASSIGNED → IN_PROGRESS
ASSIGNED → CANCELLED

IN_PROGRESS → COMPLETED
IN_PROGRESS → CANCELLED

COMPLETED → IN_PROGRESS
COMPLETED → CLOSED
```

Все остальные переходы запрещены.

`CLOSED` и `CANCELLED` окончательны.

### 7.3. Состояние по статусам

#### NEW

```text
assignedTechnician отсутствует
assignedAt отсутствует
startedAt отсутствует
completedAt отсутствует
closedAt отсутствует
```

#### ASSIGNED

```text
assignedTechnician указан
assignedAt указано
startedAt отсутствует
completedAt отсутствует
closedAt отсутствует
```

#### IN_PROGRESS

```text
assignedTechnician указан
assignedAt указано
startedAt указано
completedAt отсутствует
closedAt отсутствует
```

#### COMPLETED

```text
assignedTechnician указан
startedAt указано
resolution заполнено
completedAt указано
closedAt отсутствует
```

#### CLOSED

```text
resolution заполнено
completedAt указано
closedAt указано
MaintenanceRecord существует
```

#### CANCELLED

```text
cancellationReason заполнена
closedAt указано
completedAt отсутствует
MaintenanceRecord отсутствует
```

### 7.4. Кто выполняет переходы

| Переход | Кто |
|---|---|
| `NEW → ASSIGNED` | `ADMIN` |
| `NEW → CANCELLED` | `ADMIN` или автор новой заявки |
| `ASSIGNED → NEW` | `ADMIN` |
| `ASSIGNED → IN_PROGRESS` | назначенный `TECHNICIAN` |
| `ASSIGNED → CANCELLED` | `ADMIN` |
| `IN_PROGRESS → COMPLETED` | назначенный `TECHNICIAN` |
| `IN_PROGRESS → CANCELLED` | `ADMIN` |
| `COMPLETED → IN_PROGRESS` | `ADMIN` |
| `COMPLETED → CLOSED` | `ADMIN` |

## 8. Сущность MaintenanceRecord

### 8.1. Поля

| Поле | Обязательность | Назначение |
|---|---|---|
| `id` | обязательное | Уникальный идентификатор |
| `equipment` | обязательное | Оборудование |
| `repairRequest` | обязательное, уникальное | Исходная заявка |
| `performedBy` | обязательное | Исполнитель |
| `workDescription` | обязательное | Выполненная работа |
| `performedAt` | обязательное | Время завершения ремонта |
| `createdAt` | обязательное | Время записи в историю |

### 8.2. Создание

Запись создаётся только при:

```text
COMPLETED → CLOSED
```

Пользователь не заполняет её вручную.

Источник данных:

```text
MaintenanceRecord.equipment
← RepairRequest.equipment

MaintenanceRecord.repairRequest
← закрываемая RepairRequest

MaintenanceRecord.performedBy
← RepairRequest.assignedTechnician

MaintenanceRecord.workDescription
← RepairRequest.resolution

MaintenanceRecord.performedAt
← RepairRequest.completedAt

MaintenanceRecord.createdAt
← текущее время
```

```text
performedAt
= когда техник закончил ремонт

createdAt
= когда администратор принял результат
```

### 8.3. Неизменяемость

После создания запись нельзя:

- редактировать;
- удалять;
- менять исполнителя;
- менять оборудование;
- менять описание;
- менять даты.

`updatedAt` не требуется.

Отменённая заявка `MaintenanceRecord` не создаёт.

## 9. Связи и кардинальности

### 9.1. Автор заявки

```text
User 1 ───────── 0..* RepairRequest
                  createdBy
```

### 9.2. Назначенный техник

```text
User 1 ───────── 0..* RepairRequest
                  assignedTechnician
```

У заявки может быть `0..1` текущий техник.

### 9.3. Оборудование и заявки

```text
Equipment 1 ─────── 0..* RepairRequest
```

### 9.4. Заявка и история

```text
RepairRequest 1 ─────── 0..1 MaintenanceRecord
```

```text
NEW         → 0 MaintenanceRecord
ASSIGNED    → 0 MaintenanceRecord
IN_PROGRESS → 0 MaintenanceRecord
COMPLETED   → 0 MaintenanceRecord
CANCELLED   → 0 MaintenanceRecord
CLOSED      → 1 MaintenanceRecord
```

`MaintenanceRecord.repairRequest` уникально.

Отдельное поле `maintenanceRecord` в `RepairRequest` не обязательно.

### 9.5. Оборудование и история

```text
Equipment 1 ─────── 0..* MaintenanceRecord
```

Обязательная согласованность:

```text
MaintenanceRecord.equipment
=
MaintenanceRecord.repairRequest.equipment
```

### 9.6. Техник и история

```text
User 1 ─────── 0..* MaintenanceRecord
                  performedBy
```

| Активировать и деактивировать | Да | Нет | Нет |
| Физически удалять | Нет | Нет | Нет |
| Изменять собственный пароль | Да | Да | Да |

### 10.2. Equipment

| Просматривать | Да | Да | Да |
| Создавать | Да | Нет | Нет |
| Изменять | Да | Нет | Нет |
| Менять статус | Да | Нет | Нет |

### 10.3. RepairRequest

| Действие | ADMIN | TECHNICIAN | REQUESTER |
|---|---:|---:|---:|
| Создавать | Да | Да | Да |
| Выбирать начальный приоритет | Да | Да | Да |
| Менять приоритет после создания | Да | Нет | Нет |
| Назначать техника | Да | Нет | Нет |
| Начинать ремонт | Нет | Да, если назначен | Нет |
| Заполнять `resolution` | Нет | Да, если назначен | Нет |
| Переводить в `COMPLETED` | Нет | Да, если назначен | Нет |
| Возвращать в работу | Да | Нет | Нет |
| Закрывать | Да | Нет | Нет |
| Отменять собственную `NEW` | Да | Да, если автор | Да, если автор |
| Отменять после назначения | Да | Нет | Нет |

### 10.4. Просмотр заявок

`ADMIN` видит все заявки.

`TECHNICIAN` видит:

- назначенные ему;
- созданные им;
- историю оборудования для диагностики.

`REQUESTER` видит:

- собственные заявки;
- сокращённое предупреждение об открытых заявках по оборудованию;
- историю обслуживания.

### 10.5. Редактирование автором

Автор может менять `title` и `description`, если:

```text
createdBy = текущий пользователь
status = NEW
assignedTechnician отсутствует
```

Поле `equipment` после создания не меняет никто.

### 10.6. MaintenanceRecord

Доступ только для чтения.

Ни одна роль не создаёт, не редактирует и не удаляет запись вручную.

## 11. Назначение и переназначение

### 11.1. Назначение

Проверки:

```text
пользователь существует
role = TECHNICIAN
active = true
status заявки = NEW
```

Результат:

```text
assignedTechnician = выбранный техник
assignedAt = текущее время
status = ASSIGNED
updatedAt = текущее время
```

### 11.2. Снятие назначения

Разрешено только в `ASSIGNED`.

```text
status = NEW
assignedTechnician = отсутствует
assignedAt = отсутствует
```

### 11.3. Переназначение в IN_PROGRESS

```text
status = IN_PROGRESS
assignedTechnician = новый техник
assignedAt = текущее время
startedAt = прежнее значение
resolution = прежний черновик
```

Новый техник проверяет работу и сам завершает заявку.

В истории будет указан последний назначенный техник. Участие нескольких техников в MVP отдельно не хранится.

### 11.4. Переназначение в COMPLETED

Прямое переназначение запрещено.

Сначала:

```text
COMPLETED → IN_PROGRESS
```

## 12. Полный бизнес-сценарий

### 12.1. Исходные данные

```text
Anna Müller
role = REQUESTER
active = true
```

```text
Markus Schneider
role = TECHNICIAN
active = true
```

```text
Laura Wagner
role = ADMIN
active = true
```

```text
Equipment:
name = Воздушный компрессор
inventoryNumber = COMP-001
location = Цех №1
status = OPERATIONAL
```

### 12.2. Создание

Анна указывает:

```text
title = Компрессор не запускается

description =
При нажатии кнопки запуска слышен щелчок,
но двигатель не включается.
На панели отображается ошибка E-14.

equipment = COMP-001
priority = HIGH
```

Система:

```text
createdBy = Anna Müller
status = NEW
assignedTechnician = отсутствует
createdAt = текущее время
updatedAt = текущее время
```

### 12.3. Назначение

Администратор проверяет заявку и назначает Маркуса:

```text
assignedTechnician = Markus Schneider
assignedAt = текущее время
status = ASSIGNED
```

При необходимости оборудование:

```text
OPERATIONAL → OUT_OF_SERVICE
```

### 12.4. Начало ремонта

Маркус:

```text
ASSIGNED → IN_PROGRESS
startedAt = текущее время
```

При фактическом выводе в ремонт администратор:

```text
OUT_OF_SERVICE → UNDER_REPAIR
```

### 12.5. Выполнение

Техник заполняет:

```text
resolution =
Обнаружено повреждение пускового реле.
Реле заменено, контакты проверены и затянуты.
После пробного запуска компрессор работает без ошибки E-14.
```

Затем:

```text
IN_PROGRESS → COMPLETED
completedAt = текущее время
```

### 12.6. Проверка и закрытие

Администратор может:

```text
COMPLETED → IN_PROGRESS
```

для доработки, либо:

```text
COMPLETED → CLOSED
```

при принятии результата.

При исправности оборудование переводится в `OPERATIONAL`.

Закрытие одной операцией:

1. создаёт `MaintenanceRecord`;
2. устанавливает `status = CLOSED`;
3. устанавливает `closedAt`.

Если история не создана, заявка остаётся `COMPLETED`.

## 13. Валидация и целостность

### 13.1. Текст

- пробелы в начале и конце удаляются;
- строка из пробелов считается пустой;
- пустое необязательное поле хранится как отсутствие значения.

### 13.2. Уникальность

| Сущность | Поле | Правило |
|---|---|---|
| `User` | `email` | уникальное без учёта регистра |
| `Equipment` | `inventoryNumber` | уникальное без учёта регистра |
| `MaintenanceRecord` | `repairRequest` | одна запись на одну заявку |

Все `id` уникальны.

### 13.3. Проверки выполняются внутри приложения

Интерфейс помогает пользователю, но не является защитой.

Приложение повторно проверяет:

- роль;
- активность;
- авторство;
- назначение;
- текущий статус;
- допустимость перехода;
- наличие результата;
- оборудование;
- уникальность;
- отсутствие дублирующей истории.

### 13.4. Устаревшие данные

Старая версия заявки не должна незаметно перезаписывать новую.

```text
Заявка была изменена другим пользователем.
Обновите страницу и повторите действие.
```

### 13.5. Повторные действия

- двойное «Начать работу» не перезаписывает `startedAt`;
- двойное закрытие не создаёт вторую историю;
- повторный запрос не оставляет противоречивые данные.

---

## 14. Атомарность закрытия

Закрытие включает:

```text
создание MaintenanceRecord
+
изменение RepairRequest на CLOSED
```

Успех:

```text
MaintenanceRecord создан
RepairRequest.status = CLOSED
closedAt установлен
```

Ошибка:

```text
MaintenanceRecord не создан
RepairRequest.status = COMPLETED
closedAt отсутствует
```

Недопустимо закрыть заявку без истории или создать историю без закрытия в нормальном процессе.

## 15. Пограничные ситуации

### 15.1. Дубликаты

Система предупреждает об открытых заявках, но не блокирует создание автоматически.

Дубликат отменяется с указанием причины.

### 15.2. Неверное оборудование

Заявка отменяется и создаётся новая.

### 15.3. Неактивный техник

Не может быть назначен.

Старые связи сохраняются.

### 15.4. Деактивация техника с заявками

Запрещена при `ASSIGNED`, `IN_PROGRESS`, `COMPLETED`.

### 15.5. Чужая заявка

Техник не может начать или завершить заявку, если он не равен `assignedTechnician`.

### 15.6. Пустой resolution

`IN_PROGRESS → COMPLETED` запрещён.

### 15.7. Результат не принят

```text
COMPLETED → IN_PROGRESS
```

`completedAt` очищается, остальные рабочие данные сохраняются.

### 15.8. Списание с открытыми заявками

Запрещено.

### 15.9. Одновременное списание и создание заявки

Статус оборудования повторно проверяется при сохранении.

### 15.10. Удаление оборудования с историей

Запрещено; используется `DECOMMISSIONED`.

### 15.11. Деактивация автора

Не влияет на существующую заявку.

### 15.12. Последний ADMIN

Не может быть деактивирован или переведён в другую роль.

### 15.13. Сбой при закрытии

Все изменения отменяются; заявка остаётся `COMPLETED`.

### 15.14. Повторное закрытие

Не создаёт дубликат и не меняет `closedAt`.

### 15.15. Отмена во время ремонта

Выполняется только `ADMIN`.

Если выполненную работу нужно сохранить, заявка должна быть завершена и закрыта, а не отменена.

### 15.16. Повторная неисправность

Создаётся новая заявка. Закрытая не открывается повторно.

### 15.17. Ошибка в истории

В MVP закрытые заявки и `MaintenanceRecord` не редактируются.

Позже можно добавить исправляющие записи и аудит.

## 17. Итоговые бизнес-правила

1. В MVP четыре основные сущности.
2. У пользователя одна роль.
3. Самостоятельной регистрации нет.
4. Пользователи и оборудование с историей физически не удаляются.
5. Заявка всегда имеет автора и оборудование.
6. Оборудование после создания заявки не меняется.
7. Назначить можно только активного `TECHNICIAN`.
8. Начать и завершить работу может только назначенный техник.
9. `resolution` заполняет только назначенный техник.
10. `ADMIN` не выполняет этапы техника.
11. Статус заявки меняется только разрешённым переходом.
12. `COMPLETED` требует `resolution`.
13. `CANCELLED` требует `cancellationReason`.
14. `CLOSED` требует одну `MaintenanceRecord`.
15. `MaintenanceRecord` создаётся автоматически при закрытии.
16. Для одной заявки возможна только одна запись истории.
17. Закрытые, отменённые и исторические данные не редактируются.
18. Статус оборудования управляется отдельно.
19. Списанное оборудование не принимает новые заявки.
20. Ошибка не должна оставлять частично изменённые данные.
21. Права проверяются по роли, авторству, назначению и статусу.
22. Повторная неисправность оформляется новой заявкой.
