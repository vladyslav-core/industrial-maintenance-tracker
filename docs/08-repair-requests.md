# 08 — Repair requests

## 1. Цель и границы этапа

Реализовать ремонтные заявки от создания до закрытия или отмены. Все правила и поля согласуются с `docs/01`, `docs/02` и `docs/03`. Код этапа 08 начинается после проверки и фиксации этих документов.

Входит:

- модель `RepairRequest`, миграция и репозиторий;
- создание заявки пользователем любой из трёх ролей;
- просмотр с ограничением по роли, поиск и фильтры;
- редактирование автором своей новой неназначенной заявки;
- назначение, снятие назначения, переназначение и изменение приоритета администратором;
- начало работы, сохранение черновика результата и завершение назначенным техником;
- возврат результата на доработку и окончательное закрытие администратором;
- отмена с обязательной причиной;
- модель `MaintenanceRecord`, миграция и атомарное создание одной записи при закрытии;
- защита списания оборудования и деактивации либо изменения роли назначенного техника при незакрытых заявках;
- страницы и проверки прав для перечисленных действий;
- необходимые тесты и небольшой набор ручных проверок.

Общая страница истории обслуживания, блок подтверждённой истории в карточке оборудования и ролевая сводка относятся к следующему этапу MVP. Нет журнала смен статусов, комментариев, вложений, запчастей, учёта часов, пагинации, автоматического назначения или автоматической смены статуса оборудования.

## 2. Поля и связи

| Сущность | Поля и ограничения |
|---|---|
| `RepairRequest` | `id` используется и как номер заявки; обязательны `title` (5–150), `description` (10–3000), `equipment`, `createdBy`, `priority`, `status`, `createdAt`, `updatedAt` |
| Назначение | `assignedTechnician` — один текущий активный `TECHNICIAN` либо отсутствие; `assignedAt` — время последнего назначения |
| Рабочий результат | `resolution` — один текст о причине, выполненных действиях и результате; обязателен перед `COMPLETED` |
| Отмена | `cancellationReason` (5–500) обязательна для `CANCELLED` |
| Время | `startedAt` — первое начало; `completedAt` — последнее завершение техником; `closedAt` — окончательное закрытие или отмена |
| `MaintenanceRecord` | `id`, `equipment`, уникальный `repairRequest`, `performedBy`, `workDescription`, `performedAt`, `createdAt`; после создания не изменяется |

Приоритеты: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`. Начальное значение выбирает автор; если оно не задано, используется `MEDIUM`. После создания только ADMIN меняет приоритет в `NEW`, `ASSIGNED` или `IN_PROGRESS`. Отдельного подтверждения `CRITICAL` нет.

Оборудование и автор после создания заявки не изменяются. Заявка не хранит отдельные дату обнаружения, местоположение или номер, отличный от `id`. Нельзя создать заявку на `DECOMMISSIONED`.

При `COMPLETED → CLOSED` в одной транзакции из заявки в запись истории переносятся оборудование, текущий техник, `resolution` и `completedAt`. Дата создания записи соответствует принятию результата администратором. Для `COMPLETED` и `CANCELLED` записи истории нет.

## 3. Статусы и переходы

| Из | В | Исполнитель и условие |
|---|---|---|
| `NEW` | `ASSIGNED` | ADMIN назначает активного техника |
| `NEW` | `CANCELLED` | ADMIN либо автор; нужна причина |
| `ASSIGNED` | `NEW` | ADMIN снимает назначение до начала работы |
| `ASSIGNED` | `IN_PROGRESS` | Текущий назначенный техник начинает работу |
| `ASSIGNED` | `CANCELLED` | ADMIN; нужна причина |
| `IN_PROGRESS` | `COMPLETED` | Текущий назначенный техник; нужен `resolution` |
| `IN_PROGRESS` | `CANCELLED` | ADMIN; нужна причина |
| `COMPLETED` | `IN_PROGRESS` | ADMIN возвращает на доработку; `completedAt` очищается, `resolution` сохраняется |
| `COMPLETED` | `CLOSED` | ADMIN принимает результат; атомарно создаётся `MaintenanceRecord` |

Переназначение в `ASSIGNED` или `IN_PROGRESS` сохраняет статус; `assignedAt` обновляется, `startedAt` и черновик `resolution` остаются. Все остальные переходы запрещены. `CLOSED` и `CANCELLED` окончательны.

## 4. Права и видимость

| Роль | Видит | Может изменить |
|---|---|---|
| ADMIN | Все заявки | Создать свою; редактировать собственную `NEW`; назначить или снять техника, поменять приоритет, отменить, вернуть `COMPLETED` и закрыть |
| TECHNICIAN | Назначенные ему и созданные им заявки | Создать свою; редактировать или отменить собственную `NEW`; начать, сохранить результат и завершить только назначенную ему заявку |
| REQUESTER | Только созданные им заявки | Создать, редактировать и отменять собственную `NEW`; просматривать результат |

ADMIN не начинает и не завершает ремонт, не заполняет `resolution`. TECHNICIAN не назначает исполнителя и не закрывает заявку. Создание заявки техником не назначает его исполнителем. Действия автора с `NEW` допустимы только до назначения.

Ограничение просмотра применяется в запросе к базе, проверка права на конкретный `id` и изменяющую операцию — в сервисе. Кнопки показываются только при доступном действии; ручной HTTP-запрос не обходит проверку. При сохранении устаревшей формы редактирования или результата проверяется `updatedAt` и выводится понятная ошибка.

## 5. Страницы и маршруты

| Маршрут | Назначение |
|---|---|
| `GET /repair-requests` | Список, поиск по `id`/заголовку/описанию, фильтры и стабильная сортировка по `createdAt`, `id` |
| `GET /repair-requests/new`, `POST /repair-requests` | Создание заявки любой ролью |
| `GET /repair-requests/{id}` | Карточка заявки и доступные по статусу действия |
| `GET /repair-requests/{id}/edit`, `POST /repair-requests/{id}/edit` | Изменение автором заголовка и описания собственной `NEW` |
| `POST /repair-requests/{id}/assign` | Назначение или переназначение ADMIN |
| `POST /repair-requests/{id}/unassign` | Снятие назначения ADMIN |
| `POST /repair-requests/{id}/priority` | Изменение приоритета ADMIN |
| `POST /repair-requests/{id}/start` | Начало работы назначенным техником |
| `GET /repair-requests/{id}/complete`, `POST /repair-requests/{id}/resolution`, `POST /repair-requests/{id}/complete` | Форма результата, сохранение черновика, завершение работы |
| `POST /repair-requests/{id}/return`, `POST /repair-requests/{id}/close` | Решение администратора после `COMPLETED` |
| `POST /repair-requests/{id}/cancel` | Отмена ADMIN либо автором собственной `NEW` с причиной |

Формы работают с CSRF. Отдельных страниц для изменения приоритета, назначения, отмены и закрытия не требуется: действия размещаются в карточке заявки. Статус не изменяется через общий выпадающий список.

## 6. Межмодульная целостность

- `EquipmentService` запрещает переход в `DECOMMISSIONED`, если по оборудованию есть `NEW`, `ASSIGNED`, `IN_PROGRESS` или `COMPLETED`.
- `UserService` запрещает деактивировать техника и менять его роль, если за ним числятся `ASSIGNED`, `IN_PROGRESS` или `COMPLETED`.
- Создание заявки и списание оборудования согласуются в транзакциях через блокировку строки оборудования. Назначение техника и изменение его роли/активности также требуют согласованной блокировки пользователя.
- Повторное закрытие не создаёт ещё одну запись истории. Если сохранение `MaintenanceRecord` не удалось, статус заявки остаётся `COMPLETED`.

## 8. Критерий завершения этапа

Три роли проходят свои разрешённые сценарии; недоступные действия блокируются на сервере. Полный цикл `NEW → ASSIGNED → IN_PROGRESS → COMPLETED → CLOSED` сохраняет одну неизменяемую запись `MaintenanceRecord`. Отмена, возврат и межмодульные ограничения проходят тесты. Документы и код соответствуют друг другу, рабочая ветка чистая после логических коммитов.
