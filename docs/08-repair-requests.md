# 08 — Repair requests

## 1. Цель и границы этапа

Этап реализует ремонтные заявки от создания до закрытия или отмены. Правила и поля согласованы с `docs/01`, `docs/02` и `docs/03`; последовательность реализации сохранена ниже. Завершение этапа требует автоматического прогона и ручной проверки из разделов 9–10.

Входит:

- модель `RepairRequest`, миграция и репозиторий;
- создание заявки пользователем любой из трёх ролей;
- просмотр с ограничением по роли, поиск и фильтры;
- редактирование автором своей новой неназначенной заявки;
- назначение, снятие назначения, переназначение и изменение приоритета администратором;
- начало работы, сохранение черновика результата и завершение назначенным техником;
- возврат результата на доработку и окончательное закрытие администратором;
- отмена с обязательной причиной;
- модель `MaintenanceRecord`, миграция и атомарное создание одной записи при закрытии;
- защита списания оборудования и деактивации либо изменения роли назначенного техника при незакрытых заявках;
- страницы и проверки прав для перечисленных действий;
- необходимые тесты и небольшой набор ручных проверок.

В исходном плане 00–16 этап 08 охватывает базовые заявки, этап 09 — их жизненный цикл. Оба реализованы вместе и описаны здесь. Общая история, история оборудования и блок доступных незакрытых заявок в его карточке относятся к [этапу 10](10-maintenance-history.md). Ролевая сводка относится к отдельному этапу. Нет журнала смен статусов, комментариев, вложений, запчастей, учёта часов, пагинации, автоматического назначения или автоматической смены статуса оборудования.

## 2. Поля и связи

| Сущность | Поля и ограничения |
|---|---|
| `RepairRequest` | `id` используется и как номер заявки; обязательны `title` (5–150), `description` (10–3000), `equipment`, `createdBy`, `priority`, `status`, `createdAt`, `updatedAt` |
| Назначение | `assignedTechnician` — один текущий активный `TECHNICIAN` либо отсутствие; `assignedAt` — время последнего назначения |
| Рабочий результат | `resolution` — один текст о причине, выполненных действиях и результате; обязателен перед `COMPLETED` |
| Отмена | `cancellationReason` (5–500) обязательна для `CANCELLED` |
| Время | `startedAt` — первое начало; `completedAt` — последнее завершение техником; `closedAt` — окончательное закрытие или отмена |
| `MaintenanceRecord` | `id`, `equipment`, уникальный `repairRequest`, `performedBy`, `workDescription`, `performedAt`, `createdAt`; после создания не изменяется |

Приоритеты: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`. Начальное значение выбирает автор; если оно не задано, используется `MEDIUM`. После создания только ADMIN меняет приоритет в `NEW`, `ASSIGNED` или `IN_PROGRESS`. Отдельного подтверждения `CRITICAL` нет.

Оборудование и автор после создания заявки не изменяются. Заявка не хранит отдельные дату обнаружения, местоположение или номер, отличный от `id`. Нельзя создать заявку на `DECOMMISSIONED`.

При `COMPLETED → CLOSED` в одной транзакции из заявки в запись истории переносятся оборудование, текущий техник, `resolution` и `completedAt`. Время принятия результата хранится в `RepairRequest.closedAt`, время сохранения записи — в `MaintenanceRecord.createdAt`. Для `COMPLETED` и `CANCELLED` записи истории нет.

## 3. Статусы и переходы

| Из | В | Исполнитель и условие |
|---|---|---|
| `NEW` | `ASSIGNED` | ADMIN назначает активного техника |
| `NEW` | `CANCELLED` | ADMIN либо автор; нужна причина |
| `ASSIGNED` | `NEW` | ADMIN снимает назначение до начала работы |
| `ASSIGNED` | `IN_PROGRESS` | Текущий назначенный техник начинает работу |
| `ASSIGNED` | `CANCELLED` | ADMIN; нужна причина |
| `IN_PROGRESS` | `COMPLETED` | Текущий назначенный техник; нужен `resolution` |
| `IN_PROGRESS` | `CANCELLED` | ADMIN; нужна причина |
| `COMPLETED` | `IN_PROGRESS` | ADMIN возвращает на доработку; `completedAt` очищается, `resolution` сохраняется |
| `COMPLETED` | `CLOSED` | ADMIN принимает результат; атомарно создаётся `MaintenanceRecord` |

Переназначение в `ASSIGNED` или `IN_PROGRESS` сохраняет статус; `assignedAt` обновляется, `startedAt` и черновик `resolution` остаются. Все остальные переходы запрещены. `CLOSED` и `CANCELLED` окончательны.

## 4. Права и видимость

| Роль | Видит | Может изменить |
|---|---|---|
| ADMIN | Все заявки | Создать свою; редактировать собственную `NEW`; назначить или снять техника, поменять приоритет, отменить, вернуть `COMPLETED` и закрыть |
| TECHNICIAN | Назначенные ему и созданные им заявки | Создать свою; редактировать или отменить собственную `NEW`; начать, сохранить результат и завершить только назначенную ему заявку |
| REQUESTER | Только созданные им заявки | Создать, редактировать и отменять собственную `NEW`; просматривать результат |

ADMIN не начинает и не завершает ремонт, не заполняет `resolution`. TECHNICIAN не назначает исполнителя и не закрывает заявку. Создание заявки техником не назначает его исполнителем. Действия автора с `NEW` допустимы только до назначения.

Ограничение просмотра применяется в запросе к базе, проверка права на конкретный `id` и изменяющую операцию — в сервисе. Кнопки показываются только при доступном действии; ручной HTTP-запрос не обходит проверку. При сохранении устаревшей формы редактирования или результата проверяется `updatedAt` и выводится понятная ошибка.

## 5. Страницы и маршруты

| Маршрут | Назначение |
|---|---|
| `GET /repair-requests` | Список, поиск по `id`/заголовку/описанию, фильтры и стабильная сортировка по `createdAt`, `id` |
| `GET /repair-requests/new`, `POST /repair-requests` | Создание заявки любой ролью |
| `GET /repair-requests/{id}` | Карточка заявки и доступные по статусу действия |
| `GET /repair-requests/{id}/edit`, `POST /repair-requests/{id}/edit` | Изменение автором заголовка и описания собственной `NEW` |
| `POST /repair-requests/{id}/assign` | Назначение или переназначение ADMIN |
| `POST /repair-requests/{id}/unassign` | Снятие назначения ADMIN |
| `POST /repair-requests/{id}/priority` | Изменение приоритета ADMIN |
| `POST /repair-requests/{id}/start` | Начало работы назначенным техником |
| `GET /repair-requests/{id}/complete`, `POST /repair-requests/{id}/resolution`, `POST /repair-requests/{id}/complete` | Форма результата, сохранение черновика, завершение работы |
| `POST /repair-requests/{id}/return`, `POST /repair-requests/{id}/close` | Решение администратора после `COMPLETED` |
| `POST /repair-requests/{id}/cancel` | Отмена ADMIN либо автором собственной `NEW` с причиной |

Формы работают с CSRF. Отдельных страниц для изменения приоритета, назначения, отмены и закрытия не требуется: действия размещаются в карточке заявки. Статус не изменяется через общий выпадающий список.

## 6. Межмодульная целостность

- `EquipmentService` запрещает переход в `DECOMMISSIONED`, если по оборудованию есть `NEW`, `ASSIGNED`, `IN_PROGRESS` или `COMPLETED`.
- `UserService` запрещает деактивировать техника и менять его роль, если за ним числятся `ASSIGNED`, `IN_PROGRESS` или `COMPLETED`.
- Создание заявки и списание оборудования согласуются в транзакциях через блокировку строки оборудования. Назначение техника и изменение его роли/активности также требуют согласованной блокировки пользователя.
- Повторное закрытие не создаёт ещё одну запись истории. Если сохранение `MaintenanceRecord` не удалось, статус заявки остаётся `COMPLETED`.

## 8. Критерий завершения этапа

Три роли проходят свои разрешённые сценарии; недоступные действия блокируются на сервере. Полный цикл `NEW → ASSIGNED → IN_PROGRESS → COMPLETED → CLOSED` сохраняет одну неизменяемую запись `MaintenanceRecord`. Отмена, возврат и межмодульные ограничения проходят тесты. Документы и код соответствуют друг другу, рабочая ветка чистая после логических коммитов.

## 9. Автоматическая проверка

| Уровень | Тесты и назначение |
|---|---|
| Домен | `*RulesTest`: разрешённые переходы, обязательные поля и сохранение результата и времени |
| MVC | `*ControllerTest`: маршруты, права, CSRF, ошибки форм и безопасный вывод текста |
| JPA и сервисы | PostgreSQL 18 через Testcontainers: видимость, устаревшие формы, реальные commit/rollback и ограничения между модулями |
| Конкурентные операции | `RepairRequestClosureTest`, `RepairRequestCancellationTest`, `RepairRequestIntegrityTest`: повторное закрытие, отмена против завершения, создание против списания и назначение против изменений аккаунта |
| Приложение целиком | `RepairRequestWorkflowTest`: настоящий вход через `/login`, сессии, CSRF из HTML, реальные контроллеры, сервисы, Thymeleaf и PostgreSQL без подмены сервисов |

`RepairRequestWorkflowTest` проводит создание, редактирование, назначение и снятие назначения, начало работы, сохранение черновика, завершение, возврат, переназначение и закрытие. Дополнительно проверяются отмена каждой ролью своей `NEW`, фильтры без расширения видимости, чужие `id`, устаревшие формы, ограничения оборудования и пользователей через HTTP. Каждый изменяющий маршрут проверяется без CSRF и с неправильным токеном. Сессия со старой ролью или активностью не обходит проверки ремонтных заявок в сервисе.

Для редактирования и рабочего результата конфликт возвращает HTTP `409`, сохраняет введённый текст и отключает сохранение до перезагрузки формы. Для устаревшего решения администратора или отмены выполняется возврат в карточку с сообщением. `updatedAt` проверяется на сервере; скрытое поле само по себе не даёт права изменить заявку.

Полный прогон с работающим Docker Desktop:

```powershell
.\mvnw.cmd test
git diff --check
```

Отдельный прогон нового сквозного набора:

```powershell
.\mvnw.cmd "-Dtest=RepairRequestWorkflowTest" test
```

Автоматические проверки используют собственные контейнеры PostgreSQL. Отсутствие ошибок в тестах не заменяет ручную приёмку интерфейса.

## 10. Ручная приёмка трёх ролей

### Подготовка

1. Запустить Docker Desktop и `docker compose up -d`.
2. Запустить `IndustrialMaintenanceTrackerApplication` из IntelliJ IDEA с настройками БД из локального `.env`, как описано в [этапе 05](05-spring-boot-project-and-technical-skeleton.md). Для пустой БД нужны также `APP_ADMIN_USERNAME` и `APP_ADMIN_PASSWORD` из [этапа 06](06-users-roles-and-security.md).
3. Войти как ADMIN. Через `/users` создать отдельные тестовые аккаунты TECHNICIAN и REQUESTER с самостоятельно выбранными паролями.
4. Создать отдельную единицу оборудования с уникальным инвентарным номером, например `STAGE08-001`. На ней выполнить проверки ниже, чтобы другие рабочие заявки не мешали проверке освобождения ресурсов.
5. Для смены роли выходить через `Sign out` и входить другим аккаунтом либо использовать отдельные профили браузера. Две обычные вкладки одного профиля используют одну сессию.

### Создание, видимость и устаревшая форма

- [ ] REQUESTER создаёт заявку на тестовое оборудование. Без выбора приоритета устанавливается `MEDIUM`; заявка получает `NEW`, техника нет.
- [ ] REQUESTER открывает редактирование в двух вкладках. После сохранения первой вкладки отправка второй не перезаписывает данные: появляется сообщение о конфликте, введённый текст остаётся, кнопка сохранения скрывается. Перезагрузка формы возвращает актуальные данные.
- [ ] TECHNICIAN до назначения не видит эту заявку в списке и получает страницу недоступной заявки при открытии её прямого URL.
- [ ] ADMIN видит заявку и назначает тестового техника. Статус становится `ASSIGNED`; у автора исчезают редактирование и отмена.
- [ ] Поиск по номеру и тексту, фильтры по статусу, приоритету, оборудованию и технику работают в пределах доступных заявок. У TECHNICIAN работают `Created by me` и `Assigned to me`.

### Работа, возврат и принятие

- [ ] Назначенный TECHNICIAN видит заявку и нажимает `Start work`: появляется `IN_PROGRESS` и время первого начала.
- [ ] TECHNICIAN сохраняет черновик. Он восстанавливается после перезагрузки формы; автор до завершения не видит черновик как готовый результат.
- [ ] Завершение с пустым результатом показывает ошибку. После заполнения результата появляется `COMPLETED` и время завершения, но ещё нет времени окончательного закрытия.
- [ ] До принятия результата ADMIN получает понятную ошибку при списании оборудования, деактивации техника и смене его роли. Активность, роль и статус оборудования остаются прежними.
- [ ] REQUESTER видит результат, но не может принять его или вернуть на доработку. ADMIN видит оба действия.
- [ ] ADMIN возвращает работу: `IN_PROGRESS`, время завершения очищается, текст и первое время начала сохраняются.
- [ ] TECHNICIAN исправляет результат и завершает работу повторно. ADMIN принимает её: `CLOSED`, время закрытия заполнено, кнопки изменения заявки исчезают.

### Отмена и ограничения

- [ ] TECHNICIAN создаёт вторую заявку на то же оборудование. Создание не назначает его исполнителем автоматически. REQUESTER не видит эту чужую заявку, включая прямой URL.
- [ ] TECHNICIAN отменяет свою вторую `NEW`: причина короче 5 символов отклоняется, корректная причина сохраняется. Появляется `CANCELLED` и время отмены, повторного открытия нет.
- [ ] Когда первая заявка `CLOSED`, а вторая `CANCELLED`, ADMIN может деактивировать тестового техника и списать тестовое оборудование. Финальные заявки остаются доступны ADMIN с прежним результатом или причиной отмены.

### Проверка записи истории

При приёмке этапов 08–09 итог проверяется чтением БД. Проверки страниц истории приведены в [этапе 10](10-maintenance-history.md). Команда ниже использует локальные значения из `.env.example`; если в `.env` другие имена пользователя или БД, подставить их. Выполнить её для номера закрытой заявки, затем для номера отменённой:

```powershell
$stage08RequestId = 123
docker compose exec postgres psql -U maintenance_user -d industrial_maintenance -c "SELECT rr.id, rr.status, rr.completed_at, rr.closed_at, mr.id AS maintenance_id, mr.performed_by_id, mr.performed_at, mr.work_description FROM repair_requests rr LEFT JOIN maintenance_records mr ON mr.repair_request_id = rr.id WHERE rr.id = $stage08RequestId;"
```

- [ ] Для `CLOSED` существует ровно одна запись: `work_description` совпадает с принятым результатом, `performed_by_id` — с текущим на момент закрытия техником, `performed_at` — с `completed_at` заявки.
- [ ] Для `CANCELLED` поле `maintenance_id` пустое.

Чек-лист фиксирует ожидаемое поведение; отметки проставляются после выполнения. Этап принимается после успешного полного автоматического прогона и ручной проверки.
