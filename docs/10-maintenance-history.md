## 1. Что входит в этап

| Где | Что получает пользователь |
|---|---|
| Карточка оборудования | Два отдельных блока. В первом — доступные пользователю незакрытые заявки. Во втором — все подтверждённые ремонты этой единицы оборудования. |

## 2. Контракт строки истории

В таблице `mr` — сохранённый `MaintenanceRecord`, `rr` — его `repairRequest` в статусе `CLOSED`. Подписи ниже относятся к обоим экранам.

| Подпись в интерфейсе | Откуда берётся значение | Как показываем |
|---|---|---|
| Equipment | `mr.equipment.id`, `mr.equipment.name`, `mr.equipment.inventoryNumber` | На общей странице — ссылка вида `Press A (HIST10-A)`. В карточке достаточно названия и инвентарного номера в шапке. |
| Request | `rr.id`, `rr.title` | Номер в виде `#123` и заголовок. Только номер становится ссылкой при наличии права. |
| Request created | `rr.createdAt` | Время регистрации исходной заявки. |
| Author | `rr.createdBy.fullName` | Имя автора заявки. |
| Problem description | `rr.description` | Полный текст исходной проблемы. |
| Technician | `mr.performedBy.fullName` | Имя исполнителя, на которого указывает запись истории. При закрытии сохраняется ссылка на последнего назначенного техника. |
| Repair result | `mr.workDescription` | Принятый текст, скопированный из `rr.resolution` при закрытии. |
| Completed by technician | `mr.performedAt` | Скопировано из `rr.completedAt`. После доработки это время последнего завершения техником. |
| Closed | `rr.closedAt` | Момент принятия результата администратором. |

На момент завершения этапа 10 три отображаемые даты выводятся как `Instant` в ISO 8601 UTC с явным `Z`, как временные отметки в существующей карточке заявки. Например, `2026-11-05T09:15:00Z`. Единое представление дат при оформлении задаёт [этап 11](11-dashboard-and-ui.md); источники полей и исходные `Instant` сохраняются. Закрытие вызывает `request.close(Instant.now())`, а Hibernate отдельно устанавливает `mr.createdAt` при вставке. Это четвёртая, техническая отметка. Она хранится в БД и не выводится в колонке **Closed**. [Операция закрытия](../src/main/java/com/vladyslav/industrialmaintenancetracker/repairrequest/RepairRequestService.java) · [Поля записи](../src/main/java/com/vladyslav/industrialmaintenancetracker/maintenance/MaintenanceRecord.java)

Имена людей, название и инвентарный номер читаются по сохранённым ссылкам. Переименование меняет отображаемую подпись. Деактивация техника, смена его роли или списание оборудования сохраняют доступ к записи для действующих пользователей. Текстовые поля выводятся с экранированием HTML, описание проблемы и результат сохраняют переносы строк.

История на обоих экранах упорядочена по `mr.performedAt DESC, mr.id DESC`. Первым виден последний ремонт по времени выполнения, даже если администратор позднее принял более старую работу. Второй ключ задаёт порядок при одинаковом времени. Такой порядок по единице оборудования поддерживает [индекс V5](../src/main/resources/db/migration/V5__create_maintenance_records_table.sql).

## 3. Права и незакрытые заявки

Права в таблице относятся к активной учётной записи.

| Роль | Незакрытые заявки этого оборудования | История в карточке | Общая история, в том числе с фильтром | Открытие исходной заявки |
|---|---|---|---|---|
| ADMIN | Все | Вся | Вся | Любая |
| TECHNICIAN | Назначенные ему **или** созданные им | Вся | Вся | Назначенная ему или созданная им |
| REQUESTER | Созданные им | Вся | HTTP 403 | Созданная им |

В блок **Open repair requests** входят `NEW`, `ASSIGNED`, `IN_PROGRESS` и `COMPLETED`. При `COMPLETED` техник уже сообщил результат, а решение администратора ещё впереди. После `CLOSED` тот же номер появляется только в **Maintenance history**. `CANCELLED` отсутствует в обоих блоках. Отбор одного оборудования, четырёх статусов и доступного пользователю набора заявок выполняется в запросе к БД.

В строке незакрытой заявки показываем номер-ссылку, заголовок, статус, приоритет и назначенного техника. Для неназначенной выводим **Not assigned**. Порядок — `rr.createdAt DESC, rr.id DESC`, как в списке заявок. Техник, который одновременно автор и исполнитель, видит одну строку. При отсутствии доступных заявок блок показывает **No open repair requests.** Количество чужих заявок также скрыто.

Открытие `GET /repair-requests/{requestId}` проходит через существующие `RepairRequestService.getDetails` и `RepairRequestRepository.findVisibleById`. Для активного пользователя чужой и отсутствующий номера дают одинаковые HTTP 404 и страницу **Request unavailable**. В строке истории право на ссылку вычисляется на сервере по автору и назначению **исходной заявки**. Право читать историю оборудования само по себе разрешает увидеть поля из раздела 2.

## 4. Страницы и маршруты

| GET | Поведение |
|---|---|
| `/` | Ссылка **Maintenance history** видна ADMIN и TECHNICIAN. |
| `/equipment/{equipmentId}` | Шапка оборудования и два блока из раздела 1, включая списанное оборудование. Пустая история — **No maintenance records found.** При неизвестном ID сохраняется существующий редирект на `/equipment` с сообщением об ошибке. |
| `/maintenance-history` | По умолчанию — все записи. Выбор **Equipment** содержит **All equipment** и каждую единицу (название и инвентарный номер), включая списанные и ещё не имеющие истории. Порядок вариантов — название, затем инвентарный номер. |
| `/maintenance-history?equipmentId={equipmentId}` | **Apply** применяет фильтр, выбранное оборудование остаётся в поле. **Clear** возвращает на `/maintenance-history`. Ссылка оборудования ведёт на `/equipment/{equipmentId}`. |
| `/repair-requests/{requestId}` | Существующая карточка заявки с проверкой прав из раздела 3. |

Для общей страницы фиксируем различие между пустым результатом и ошибкой ввода. Без `equipmentId` или с пустым значением выводятся все записи. Существующее оборудование без истории даёт HTTP 200 и **No maintenance records found.** Несуществующий положительный ID даёт 404 и страницу **Equipment unavailable** со ссылкой **Back to maintenance history**. Нечисловое, нулевое, отрицательное или выходящее за пределы `Long` значение даёт 400. Ошибочное значение фильтра не открывает полный список. Анонимный посетитель защищённой страницы перенаправляется на `/login`. Для REQUESTER прямой запрос общей страницы с фильтром и без него даёт 403.

## 5. Техническое решение

1. **Чтение истории.** `MaintenanceRecordRepository.findHistory` выбирает записи с `JOIN FETCH` оборудования, закрытой заявки, её автора и исполнителя записи, а также `LEFT JOIN FETCH` назначенного техника заявки. Для карточки ID оборудования обязателен. Общий список может охватывать всё оборудование. Чтение учитывает и деактивированных людей, и списанные единицы. В `MaintenanceRecordService.getHistoryPage` варианты фильтра берутся из `EquipmentRepository.search("", null)` и преобразуются в `EquipmentListItem`. Список `RepairRequestService.availableEquipment()` предназначен для создания заявки и исключает списанные единицы.
2. **Текущий пользователь.** Контроллер получает ID из `@AuthenticationPrincipal CustomUserDetails`. Сервис загружает `User` по этому ID и проверяет текущие активность и роль, в том числе при старой сессии. Параметры URL не задают `viewerId` или роль. У `MaintenanceRecordService` раздельные операции `getEquipmentHistory`, `getHistory` и сборка общей страницы `getHistoryPage`. Общая операция проверяет ADMIN/TECHNICIAN также при переданном фильтре. В `SecurityConfig` правило ролей для `GET /maintenance-history` стоит перед `anyRequest().authenticated()`.
3. **Видимость заявок.** `RepairRequestRepository.findVisibleOpenByEquipment` отбирает оборудование и четыре незакрытых статуса с тем же предикатом, что в `findVisibleById`: ADMIN, автор или TECHNICIAN, назначенный на эту заявку. Левое соединение для необязательного назначения сохраняет видимые `NEW`. В истории флаг `canViewRequest` вычисляется по роли, ID автора и назначенного техника исходной заявки. Прямой GET по-прежнему проверяет сервис заявок. Дополнительный запрос на каждую строку истории не выполняется.
4. **Сборка страниц.** `EquipmentController` получает `EquipmentDetailsPage` от `EquipmentDetailsService`. Шапка, история и открытые заявки собираются в одной короткой транзакции чтения с изоляцией `REPEATABLE_READ`. Оба блока отражают один снимок базы, даже если заявку закроют между двумя SELECT. Общая страница использует `MaintenanceHistoryPage` и обычную `@Transactional(readOnly = true)`. В Thymeleaf передаются DTO с готовыми полями и разрешёнными ссылками. При `spring.jpa.open-in-view=false` шаблон не загружает связи. Оба экрана используют фрагмент `records` из `templates/maintenance/history.html`; фрагмент `history` добавляет заголовок блока в карточке.
5. **Только чтение и ошибки фильтра.** `MaintenanceRecordController` обслуживает GET общей страницы. `@Positive` и преобразование в `Long` обеспечивают 400 для неверного фильтра; `EquipmentNotFoundException` обрабатывается как 404. Есть GET-форма фильтра, маршрутов создания, редактирования или удаления истории нет. Существующие `closeRequest`, ограничения списания и деактивации, миграции V4/V5 продолжают обслуживать запись данных. Этап читает накопленную историю без новых миграций и пересоздания записей.

Основу сохраняют `MaintenanceRecordRepositoryTest` (снимок, уникальность, внешняя связь), `RepairRequestClosureTest` (повторное и конкурентное закрытие, откат, доработка) и `RepairRequestIntegrityTest` (списание и изменения аккаунта). Чтение и экраны проверяют `MaintenanceRecordServiceTest`, `MaintenanceHistoryReadTest`, `MaintenanceRecordControllerTest`, `EquipmentReadControllerTest`, `RepairRequestReadTest` и `RepairRequestWorkflowTest`.

| Уровень | Покрытие |
|---|---|
| JPA, PostgreSQL 18 | Две единицы оборудования, несколько записей, фильтр и пустой результат. Порядок по `performedAt` и по ID записи при равенстве. В фикстуре развести `rr.createdAt`, `mr.performedAt`, `rr.closedAt` и `mr.createdAt` и проверить все три показываемые даты. |

## 7. Ручная приёмка после реализации

Все пути ниже отсчитываются от `http://localhost:8080`. Это сценарий повторной приёмки на тестовых данных; уже выполненные проверки зафиксированы в разделе 9. Подставлять фактические числовые ID из адресной строки. Например, для оборудования 7 и заявки 73 это `/equipment/7`, `/maintenance-history?equipmentId=7`, `/repair-requests/73`. Английские подписи соответствуют реализованному интерфейсу.

**Подготовка.** Запустить приложение с локальной БД по [инструкции этапа 05](05-spring-boot-project-and-technical-skeleton.md). Для теста нужны ADMIN, два активных техника T1/T2 и два сотрудника R1/R2. Войти на `/login` — **Sign in** (войти). При необходимости под ADMIN открыть `/users/new` — **Create user** (создать пользователя). На `/equipment/new` дважды выполнить **Add equipment** (добавить оборудование). Назвать единицы `Press A` и `Press B`, указать инвентарные номера `HIST10-A` и `HIST10-B` либо другие свободные. Записать ID как A и B. Для смены пользователя на `/` нажать **Sign out** (выйти) и на `/login` — **Sign in** (войти), либо использовать разные профили браузера.
