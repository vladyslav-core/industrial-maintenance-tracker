# 02 — Пользовательские сценарии и экраны

## 1. Цель этапа

На этом этапе определяется, как пользователи взаимодействуют с Industrial Maintenance Tracker:

* какие страницы существуют;
* какие данные отображаются;
* какие действия доступны каждой роли;
* как заявка проходит путь от создания до завершения ремонта;
* какие изменения статуса разрешены.

Техническая реализация, структура базы данных, REST API и Spring Boot пока не рассматриваются.

---

# 2. Основные решения MVP

Для первой версии принимаются следующие правила:

1. В системе существуют три роли:

   * `ADMIN`;
   * `TECHNICIAN`;
   * `REQUESTER`.

2. Один пользователь имеет одну роль.

3. Самостоятельной регистрации нет. Пользователей создаёт администратор.

4. Одна заявка относится к одной единице оборудования.

5. У одной заявки может быть только один назначенный техник.

6. История обслуживания создаётся автоматически после завершения заявки.

7. Завершённые и отменённые заявки являются конечными и больше не изменяют статус.

8. Если после завершения ремонта проблема появилась снова, создаётся новая заявка. Старая заявка повторно не открывается.

Это специально упрощает MVP и предотвращает появление сложной логики повторного открытия, согласования и версий отчётов.

---

# 3. Навигация по ролям

## ADMIN

Главное меню:

* Главная;
* Заявки;
* Оборудование;
* История обслуживания;
* Пользователи;
* Выход.

## TECHNICIAN

Главное меню:

* Главная;
* Мои заявки;
* Оборудование;
* История обслуживания;
* Выход.

## REQUESTER

Главное меню:

* Главная;
* Создать заявку;
* Мои заявки;
* Оборудование;
* Выход.

# 4. Страницы приложения

## 4.1. Страница входа

### Что отображается

* название приложения;
* поле логина или электронной почты;
* поле пароля;
* кнопка «Войти»;
* сообщение об ошибке при неправильных данных.

### Доступ

Страница доступна всем неавторизованным пользователям.

### Поведение после входа

После успешного входа пользователь переходит на главную страницу своей роли.

Самостоятельное восстановление пароля и регистрация в MVP не входят.

---

## 4.2. Главная страница ADMIN

### Что отображается

Карточки со сводной информацией:

* новые неназначенные заявки;
* назначенные заявки;
* заявки в работе;
* недавно завершённые заявки;
* количество активного оборудования;
* количество активных пользователей.

Также отображается список последних заявок.

### Доступные действия

* открыть неназначенные заявки;
* открыть конкретную заявку;
* назначить техника;
* перейти к управлению оборудованием;
* перейти к управлению пользователями.

Главная страница должна помогать администратору быстро увидеть заявки, которые требуют его действий.

---

## 4.3. Главная страница TECHNICIAN

### Что отображается

* новые назначенные ему заявки;
* заявки, которые уже находятся в работе;
* недавно завершённые им заявки;
* краткая информация об оборудовании из активных заявок.

### Доступные действия

* открыть назначенную заявку;
* начать выполнение заявки;
* продолжить работу с активной заявкой;
* открыть оборудование;
* открыть историю обслуживания оборудования.

Техник не должен видеть элементы управления пользователями или редактирования оборудования.

---

## 4.4. Главная страница REQUESTER

### Что отображается

* кнопка «Создать заявку»;
* собственные активные заявки;
* недавно завершённые собственные заявки;
* статус каждой заявки;
* дата последнего изменения.

### Доступные действия

* создать заявку;
* открыть собственную заявку;
* отменить новую заявку;
* посмотреть результат выполненного ремонта;
* открыть список оборудования.

REQUESTER не видит заявки других пользователей.

---

# 5. Оборудование

## 5.1. Список оборудования

### Что отображается

Для каждой единицы оборудования:

* инвентарный номер;
* название;
* местоположение;
* статус.

### Общие действия

Все авторизованные роли могут:

* просматривать список оборудования;
* искать оборудование по названию или инвентарному номеру;
* фильтровать оборудование по статусу;
* открыть карточку оборудования.

### ADMIN дополнительно может

* добавить оборудование;
* редактировать основные данные;
* изменить статус оборудования.

Физическое удаление оборудования через пользовательский интерфейс не используется.

### TECHNICIAN и REQUESTER

`TECHNICIAN` и `REQUESTER` могут просматривать оборудование, но не могут создавать, редактировать или изменять его статус.

После реализации заявок пользователь сможет создать заявку для оборудования, если его статус не равен `DECOMMISSIONED`.

---

## 5.2. Карточка оборудования

### Основная информация

* инвентарный номер;
* название;
* дополнительное описание;
* местоположение;
* статус;
* дата создания;
* дата последнего изменения.

### Дополнительные блоки

После реализации заявок и истории обслуживания в карточке появятся:

* открытые заявки;
* завершённые ремонты;
* история обслуживания.

На этапе реализации самого оборудования эти блоки ещё не отображаются.

Все авторизованные роли могут просматривать карточку оборудования.

Только `ADMIN` может:

* открыть форму редактирования;
* изменить статус оборудования.

---

## 5.3. Создание и редактирование оборудования

Страницы доступны только `ADMIN`.

### Поля создания

* инвентарный номер;
* название;
* дополнительное описание;
* местоположение.

При создании статус автоматически устанавливается в:

```text
OPERATIONAL
```

Пользователь не выбирает начальный статус вручную.

### Поля редактирования

* инвентарный номер;
* название;
* дополнительное описание;
* местоположение.

Статус не является частью обычной формы редактирования и изменяется отдельной операцией.

### Действия

* сохранить;
* отменить;
* перейти к отдельному изменению статуса.

Статус `DECOMMISSIONED` является окончательным. Восстановление списанного оборудования в MVP не поддерживается.

---

# 6. Заявки на ремонт

## 6.1. Список заявок ADMIN

### Что отображается

* номер заявки;
* название проблемы;
* оборудование;
* автор заявки;
* назначенный техник;
* статус;
* дата создания;
* дата последнего изменения.

### Фильтры

* статус;
* оборудование;
* автор;
* техник;
* дата создания.

### Действия

* открыть заявку;
* назначить техника;
* изменить назначенного техника;
* отменить заявку;
* посмотреть завершённые заявки.

По умолчанию вверху должны находиться новые неназначенные заявки.

---

## 6.2. Список заявок TECHNICIAN

### Что отображается

* заявки, назначенные текущему технику;
* статус;
* оборудование;
* описание проблемы;
* дата назначения;
* дата начала работы.

### Фильтры

* назначенные;
* в работе;
* завершённые;
* оборудование.

### Действия

* открыть заявку;
* начать работу;
* завершить ремонт;
* посмотреть предыдущую историю оборудования.

Техник не может назначать заявки другим техникам.

---

## 6.3. Список заявок REQUESTER

### Что отображается

Только заявки, созданные текущим пользователем:

* номер;
* название;
* оборудование;
* статус;
* назначенный техник, если он уже назначен;
* дата создания;
* дата завершения.

### Фильтры

* активные;
* завершённые;
* отменённые;
* оборудование.

### Действия

* открыть заявку;
* отменить новую заявку;
* посмотреть результат ремонта.

---

## 6.4. Создание заявки

Страница доступна `REQUESTER` и `ADMIN`.

### Обязательные поля

* оборудование;
* краткое название проблемы;
* подробное описание неисправности.

### Дополнительные данные

* дата и время обнаружения проблемы;
* местоположение оборудования, автоматически подставленное из его карточки.

### Действия

* создать заявку;
* отменить создание.

### Результат

После сохранения:

* заявке присваивается уникальный номер;
* устанавливается статус `NEW`;
* фиксируются автор и время создания;
* пользователь переходит на страницу созданной заявки.

Заявку нельзя создать для архивного оборудования.

Прикрепление фотографий и файлов в MVP не входит.

---

# 7. Карточка заявки

Карточка заявки является главным рабочим экраном процесса ремонта.

## 7.1. Верхняя часть

Отображается:

* номер заявки;
* название;
* текущий статус;
* оборудование;
* местоположение;
* автор заявки;
* назначенный техник;
* дата создания;
* дата назначения;
* дата начала работы;
* дата завершения.

## 7.2. Описание проблемы

Отображается полный текст, введённый автором заявки.

## 7.3. История статусов

Показывается последовательность основных событий:

* заявка создана;
* техник назначен;
* работа начата;
* ремонт завершён;
* заявка отменена.

Для каждого события отображаются дата, время и пользователь, выполнивший действие.

Полноценный технический аудит всех изменений в MVP не требуется, но основные события жизненного цикла заявки должны быть видны.

## 7.4. Отчёт о выполненной работе

После завершения заявки отображается:

* описание выполненных работ;
* причина неисправности, если установлена;
* результат ремонта;
* имя техника;
* дата завершения.

## 7.5. Доступные действия по ролям

### ADMIN

Может:

* назначить техника;
* изменить назначенного техника;
* снять назначение;
* отменить заявку;
* просматривать все данные заявки.

ADMIN не должен самостоятельно начинать или завершать ремонт, если у него нет роли техника.

### TECHNICIAN

Может:

* начать назначенную ему заявку;
* заполнить отчёт;
* завершить ремонт;
* просмотреть оборудование и его историю.

Техник может изменять только заявки, назначенные ему.

### REQUESTER

Может:

* просматривать собственную заявку;
* отменить заявку в статусе `NEW`;
* просматривать результат завершённого ремонта.

REQUESTER не может менять статус, назначать техника или редактировать отчёт.

---

# 8. Статусы заявки

В MVP используются пять статусов.

| Код           | Отображаемое название | Значение                                |
| ------------- | --------------------- | --------------------------------------- |
| `NEW`         | Новая                 | Заявка создана, техник ещё не назначен  |
| `ASSIGNED`    | Назначена             | Администратор назначил техника          |
| `IN_PROGRESS` | В работе              | Техник начал выполнение                 |
| `COMPLETED`   | Выполнена             | Ремонт завершён и отчёт заполнен        |
| `CANCELLED`   | Отменена              | Заявка отменена и больше не выполняется |

---

# 9. Разрешённые переходы между статусами

Основной путь:

```text
NEW → ASSIGNED → IN_PROGRESS → COMPLETED
```

Возможная отмена:

```text
NEW → CANCELLED
ASSIGNED → CANCELLED
IN_PROGRESS → CANCELLED
```

Административный возврат:

```text
ASSIGNED → NEW
IN_PROGRESS → ASSIGNED
```

## Таблица переходов

| Текущий статус | Новый статус  | Кто выполняет          | Условие                                    |
| -------------- | ------------- | ---------------------- | ------------------------------------------ |
| `NEW`          | `ASSIGNED`    | ADMIN                  | Выбран активный техник                     |
| `NEW`          | `CANCELLED`   | REQUESTER или ADMIN    | Указана причина отмены                     |
| `ASSIGNED`     | `IN_PROGRESS` | Назначенный TECHNICIAN | Техник нажал «Начать работу»               |
| `ASSIGNED`     | `NEW`         | ADMIN                  | Назначение снято                           |
| `ASSIGNED`     | `CANCELLED`   | ADMIN                  | Указана причина отмены                     |
| `IN_PROGRESS`  | `COMPLETED`   | Назначенный TECHNICIAN | Заполнен обязательный отчёт                |
| `IN_PROGRESS`  | `ASSIGNED`    | ADMIN                  | Требуется сменить техника; указана причина |
| `IN_PROGRESS`  | `CANCELLED`   | ADMIN                  | Указана причина отмены                     |

## Запрещённые переходы

Нельзя:

* перейти из `NEW` сразу в `IN_PROGRESS`;
* завершить неназначенную заявку;
* завершить заявку без отчёта;
* технику начать чужую заявку;
* вернуть `COMPLETED` в работу;
* вернуть `CANCELLED` в работу;
* удалить завершённую заявку.

Если проблема не устранена, должна создаваться новая заявка.

# 10. Полный путь REQUESTER

## Шаг 1. Вход

Пользователь вводит логин и пароль.

## Шаг 2. Главная страница

Пользователь видит собственные активные заявки и кнопку «Создать заявку».

## Шаг 3. Выбор оборудования

Пользователь открывает список оборудования и выбирает неисправное оборудование.

## Шаг 4. Создание заявки

Пользователь:

* указывает название проблемы;
* описывает неисправность;
* отправляет заявку.

Заявка получает статус `NEW`.

## Шаг 5. Ожидание обработки

Пользователь видит, что заявка создана.

После назначения техника статус меняется на `ASSIGNED`.

## Шаг 6. Выполнение ремонта

После начала работы статус меняется на `IN_PROGRESS`.

Пользователь может просматривать статус, но не вмешивается в обработку.

## Шаг 7. Завершение

После завершения ремонта статус меняется на `COMPLETED`.

Пользователь видит:

* кто выполнял ремонт;
* что было сделано;
* когда ремонт был завершён;
* результат работы.

Если неисправность осталась, пользователь создаёт новую заявку.

---

# 11. Полный путь ADMIN

## Шаг 1. Вход

Администратор переходит на главную страницу.

## Шаг 2. Обнаружение новой заявки

В блоке новых заявок появляется неназначенная заявка.

## Шаг 3. Проверка заявки

Администратор открывает заявку и проверяет:

* оборудование;
* автора;
* описание проблемы;
* наличие активных заявок по тому же оборудованию.

Автоматическое обнаружение дубликатов в MVP не требуется.

## Шаг 4. Назначение техника

Администратор выбирает активного техника.

Статус меняется:

```text
NEW → ASSIGNED
```

## Шаг 5. Контроль выполнения

Администратор видит изменение статуса:

```text
ASSIGNED → IN_PROGRESS
```

При необходимости администратор может сменить техника.

## Шаг 6. Завершение процесса

После заполнения техником отчёта заявка получает статус `COMPLETED`.

Администратор может открыть отчёт и историю обслуживания оборудования.

---

# 12. Полный путь TECHNICIAN

## Шаг 1. Вход

Техник видит назначенные ему заявки.

## Шаг 2. Открытие заявки

Техник изучает:

* описание проблемы;
* данные оборудования;
* местоположение;
* предыдущую историю обслуживания.

## Шаг 3. Начало работы

Техник нажимает «Начать работу».

Статус меняется:

```text
ASSIGNED → IN_PROGRESS
```

Фиксируются пользователь и время начала.

## Шаг 4. Выполнение ремонта

Заявка остаётся в статусе `IN_PROGRESS`.

Отдельный учёт пауз, времени работы, запчастей и промежуточных операций в MVP не ведётся.

## Шаг 5. Заполнение отчёта

Техник указывает:

* какие работы выполнены;
* какая неисправность была обнаружена;
* устранена ли проблема;
* итоговый результат.

## Шаг 6. Завершение

Техник нажимает «Завершить ремонт».

Статус меняется:

```text
IN_PROGRESS → COMPLETED
```

После этого отчёт становится доступен администратору и автору заявки.

---

# 13. История обслуживания

## 13.1. Формирование записи

Отдельно создавать запись истории обслуживания не нужно.

После перехода заявки в `COMPLETED` система автоматически формирует запись, содержащую:

* оборудование;
* ссылку на заявку;
* описание неисправности;
* выполненные работы;
* техника;
* дату начала;
* дату завершения;
* результат ремонта.

Это исключает дублирование данных и ситуации, когда заявка завершена, но запись в истории забыли создать.

## 13.2. Страница истории обслуживания

### ADMIN видит

* всю историю;
* фильтры по оборудованию;
* фильтры по технику;
* фильтры по датам;
* переход к заявке;
* переход к оборудованию.

### TECHNICIAN видит

* историю всего доступного оборудования;
* собственные выполненные работы;
* переход к оборудованию и завершённой заявке.

### REQUESTER

Отдельную общую страницу истории обслуживания не видит.

Он видит только результат собственных завершённых заявок.

---

# 14. Управление пользователями

Раздел доступен только `ADMIN`.

## 14.1. Список пользователей

Отображается:

* имя;
* логин или электронная почта;
* роль;
* активность;
* дата создания.

### Действия

* создать пользователя;
* открыть пользователя;
* изменить данные;
* изменить роль;
* деактивировать;
* активировать.

## 14.2. Карточка пользователя

### Поля

* имя;
* логин или электронная почта;
* роль;
* активность.

Пользователя, связанного с заявками, нельзя физически удалить. Его можно только деактивировать.

Деактивированного техника нельзя назначать на новые заявки.

---

# 15. Системные страницы

Дополнительно нужны простые страницы:

* «Доступ запрещён»;
* «Страница не найдена»;
* «Произошла ошибка».

Они не содержат бизнес-логики, но необходимы для нормального пользовательского опыта.

---

# 16. Что сознательно не входит в этот этап и MVP

Не проектируются:

* комментарии и чат внутри заявки;
* прикрепление фотографий и документов;
* уведомления по электронной почте;
* push-уведомления;
* склад запчастей;
* списание материалов;
* плановое техническое обслуживание;
* повторное открытие завершённых заявок;
* согласование ремонта заказчиком;
* несколько техников в одной заявке;
* учёт рабочего времени;
* SLA и автоматическая просрочка;
* QR-коды;
* аналитические отчёты;
* экспорт в PDF или Excel;
* интеграции с внешними системами.
