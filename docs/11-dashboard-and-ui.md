## 2. Общий контракт Dashboard

Dashboard доступен по `GET /` активному пользователю с одной из трёх ролей. Сверху: **Dashboard**, имя пользователя, роль, **New request** и общая навигация. Техническое сообщение **Application is running successfully.** удаляется.

Идентификатор берётся из `CustomUserDetails`, а актуальные активность и роль — из БД на сервере. Параметры вроде `viewerId`, `role`, `admin`, `technicianId`, `scope`, `limit` и `status` в URL главной не управляют выборкой. Гость перенаправляется на `/login`; отсутствующий или деактивированный аккаунт не получает данные, используется существующий отказ доступа. При несовпадении роли в principal и БД Dashboard отклоняет чтение с 403 до запросов сводки: требуется повторный вход. Обновление всех сессий приложения в этот этап не входит.

Все блоки только читают данные. Изменяющие операции остаются в карточке заявки и существующих формах. На Dashboard нет назначения, начала, завершения, отмены и закрытия в один клик.

Счётчик имеет тип `long`, считает **всю соответствующую выборку**, а не строки предпросмотра. Каждый список содержит не более **5** строк, выбранных в БД после ограничений роли и статуса. Порядок: `RepairRequest.createdAt DESC, id DESC`. Это последние созданные заявки, не последние изменения и не сортировка по срочности. После обычного обновления страницы данные читаются заново; автоматическое обновление и кеш не нужны.

Одна строка предпросмотра: номер-ссылка `#123`, заголовок, название оборудования со ссылкой, статус, приоритет, дата создания. Источники — соответственно `RepairRequest.id`, `title`, `equipment.id/name`, `status`, `priority`, `createdAt`. Можно переиспользовать `RepairRequestListItem`; Entity, описание проблемы, черновик `resolution` и чувствительные данные аккаунта в модель Dashboard не передаются. Отсутствующие строки не заменяются чужими, в том числе при пустом результате. Совпадение авторства и назначения не дублирует заявку.

## 3. Показатели, списки и источники по ролям

### 3.1. ADMIN

Источник всех показателей — `RepairRequest`, без ограничения по автору или технику. Каждая карточка содержит английскую подпись и число.

| Подпись | Точный предикат | Переход по карточке |
|---|---|---|
| New requests | `status = NEW` | `/repair-requests?status=NEW` |
| Assigned requests | `status = ASSIGNED` | `/repair-requests?status=ASSIGNED` |
| In progress | `status = IN_PROGRESS` | `/repair-requests?status=IN_PROGRESS` |
| Awaiting review | `status = COMPLETED` | `/repair-requests?status=COMPLETED` |
| Critical open requests | `priority = CRITICAL AND status IN (NEW, ASSIGNED, IN_PROGRESS, COMPLETED)` | Нет ссылки; подпись **Excludes closed and cancelled requests** поясняет состав. |

Критический показатель пересекается с первыми четырьмя: его нельзя прибавлять к ним для получения общего количества. `COMPLETED` ожидает решения ADMIN и входит в незакрытые. `CLOSED` и `CANCELLED` в него не входят.

Один список **Latest requests** — последние 5 всех заявок, включая конечные статусы. Переход **View all requests** ведёт на `/repair-requests`. Быстрые действия: **New request**, **Add equipment**, **Create user**. Остальные разделы доступны через навигацию.

### 3.2. TECHNICIAN

Для рабочей сводки обязательно `assignedTechnician.id = currentUser.id`. Само авторство не означает назначение и не увеличивает рабочие показатели.

| Блок | Точный предикат и число строк | Переход |
|---|---|---|
| Assigned to me — счётчик и список | Текущий техник назначен, `status = ASSIGNED`; счётчик всей выборки, список до 5 | `/repair-requests?scope=ASSIGNED_TO_ME&status=ASSIGNED` — **View assigned requests** |
| My work in progress — счётчик и список | Текущий техник назначен, `status = IN_PROGRESS`; счётчик всей выборки, список до 5 | `/repair-requests?scope=ASSIGNED_TO_ME&status=IN_PROGRESS` — **View work in progress** |

Собственные заявки техника, включая неназначенную `NEW`, доступны по отдельному **Created by me** → `/repair-requests?scope=CREATED_BY_ME`. Этот переход использует уже существующий фильтр. **All visible requests** ведёт на `/repair-requests`: там по прежнему правилу видны созданные им **или** назначенные ему заявки любых статусов. Дополнительный список собственных заявок на главной не дублируем.

`COMPLETED`, `CLOSED` и `CANCELLED` не входят в два рабочих показателя. Заявка одновременно своего автора и исполнителя учитывается один раз. После переназначения другому технику она исчезает из его рабочих блоков; право автора на просмотр сохраняется. Доступны **New request**, оборудование и общая история. Административных действий нет.

### 3.3. REQUESTER

Один список **My latest requests** — до 5 заявок с `createdBy.id = currentUser.id`, любых статусов, с текущими статусами. Переход **View my requests** → `/repair-requests` раскрывает полный собственный список. Главная кнопка — **New request** → `/repair-requests/new`.

Новых счётчиков для REQUESTER не добавляем: исходный план требует последние заявки и их состояние. Другие авторы, общая история `/maintenance-history` и управление пользователями отсутствуют. Оборудование и история в его карточке доступны по существующим правилам.

### 3.4. Пустые состояния

| Блок | Текст и доступное действие |
|---|---|
| ADMIN Latest requests | **No repair requests yet.** и **New request** |
| TECHNICIAN Assigned to me | **No requests assigned to you.** и **View assigned requests** |
| TECHNICIAN My work in progress | **No repairs in progress.** и **View work in progress** |
| REQUESTER My latest requests | **You have not created any requests yet.** и **New request** |

Счётчики пустых выборок показывают `0`. Нет общей строки «ещё N чужих заявок», фиктивных строк и заполнителей с демонстрационными данными.

## 4. Страницы, маршруты и навигация

Единая верхняя навигация остаётся видимой при переносе на узком экране; скрываемого за JavaScript меню не требуется. Активный раздел отмечен визуально и `aria-current="page"`. Название приложения ведёт на `/`. Выход — только POST-форма **Sign out** с действительным CSRF.

| Английская подпись | Путь | ADMIN | TECHNICIAN | REQUESTER |
|---|---|---|---|---|
| Dashboard | `/` | Да | Да | Да |
| New request | `/repair-requests/new` | Да | Да | Да |
| Repair requests | `/repair-requests` | Все | Созданные им или назначенные ему | Только собственные |
| Equipment | `/equipment` | Да | Да | Да |
| Maintenance history | `/maintenance-history` | Да | Да | Нет |
| Users | `/users` | Да | Нет | Нет |
| Sign out | `POST /logout` | Да | Да | Да |

Подпись **Repair requests** единая; пояснение видимости на странице зависит от роли. Рабочие и авторские переходы техника перечислены в §3.2. **New request** может быть главным действием в заголовке страницы; одинаковую кнопку не повторяем несколько раз рядом.

Оформляются все существующие полные страницы:

| Страницы | Маршруты/шаблоны |
|---|---|
| Главная и вход | `/` → `home.html`; `/login` → `login.html` |
| Пользователи | `/users`, `/users/new`, `/users/{id}/edit` → `users/list`, `create`, `edit` |
| Оборудование | `/equipment`, `/equipment/new`, `/equipment/{id}`, `/equipment/{id}/edit` → `equipment/list`, `create`, `details`, `edit` |
| Заявки | `/repair-requests`, `/repair-requests/new`, `/repair-requests/{id}`, `/repair-requests/{id}/edit`, `/repair-requests/{id}/complete` → `repair-requests/list`, `create`, `details`, `edit`, `resolution` |
| История | `/maintenance-history`, в том числе `?equipmentId={id}` → `maintenance/list`; `maintenance/history` остаётся общим фрагментом карточки и списка |
| Существующие страницы отказа | `/access-denied` → `access-denied`; недоступная заявка → `repair-requests/not-found`; недоступное оборудование в фильтре истории → `maintenance/not-found` |

Вход и access-denied имеют облегчённый каркас без обязательного чтения БД для меню. Прямой GET `/access-denied` остаётся существующей страницей с 200; отказ Spring Security сохраняет исходный 403 при forward. Чужая/несуществующая заявка сохраняет 404, неизвестная карточка оборудования — redirect с flash, ошибочный фильтр истории — прежний 400/404. Глобальные `error/403`, `error/404`, `error/500` и `GlobalExceptionHandler` в этом этапе не вводятся.

## 5. Визуальное направление и повторное использование

Направление: спокойный светлый рабочий интерфейс технического приложения. Белые панели на светло-сером фоне, тёмный основной текст, синий акцент для основного действия и ссылок. Без декоративных графиков, фотографий, градиентов, тяжёлых теней и отдельной тёмной темы. Язык интерфейса — английский, `lang="en"`; мультиязычность не добавляется.

| Элемент | Единое правило |
|---|---|
| Типографика | Системный sans-serif Bootstrap, основной размер 16 px, межстрочный интервал около 1.5. Один `h1`, последовательные `h2`/`h3`; подписи не заменяют label. |
| Размеры и отступы | Шкала 4/8/12/16/24/32 px. Центрированный контейнер до 1320 px, боковые поля от 16 px. Короткие формы ограничены примерно 720 px, вход — 420 px. |
| Dashboard | Карточки чисел с одинаковыми отступами. На телефоне — одна колонка; при достаточной ширине — несколько. Списки читаются без скрытия статуса и приоритета. |
| Таблицы | Общие заголовки, выравнивание, лёгкие разделители. На узком экране таблица прокручивается внутри `.table-responsive`; вся страница не должна разъезжаться. Действия переносятся и остаются доступны. |
| Формы | `form-control`/`form-select`, явные label, подсказки и ошибки рядом с полем. Сохраняются `th:object`, `th:field`, имена, значения, `updatedAt`, ограничения и `th:formaction`. Не создаём универсальный генератор форм. |
| Кнопки | Основное действие — primary, обычные переходы — ссылки/outline, отмена заявки и деактивация — danger/outline-danger. Навигация использует ссылки, изменение — submit. Существующие английские названия операций сохраняются. |
| Сообщения | `successMessage` — success, `errorMessage` и ошибки полей — danger. Сообщения об ошибке имеют `role="alert"`, успешные — `role="status"`. Существующие login error/logout оформляются тем же языком компонентов. |
| Пустые состояния | Короткое объяснение и доступное действие. В списке с фильтрами остаются выбранные фильтры и **Clear**. Поиск, параметры и поведение **Apply** не меняются. |
| Длинные тексты | Переносы слов, сохранение переводов строк описания/результата/причины. Пользовательские значения выводятся через `th:text`, без `th:utext`. Полные тексты истории не обрезаются. |
| Даты | Единое представление `yyyy-MM-dd HH:mm UTC`; исходный `Instant` сохраняется в `<time datetime="...">` как ISO 8601 с `Z`. Пустое время — **Not yet**, отсутствующий техник — **Not assigned**. Хранение, порядок и источники дат не меняются. |
| Доступность | Видимый keyboard focus, контраст текста не ниже 4.5:1, смысл статусов выражен текстом. Элементы управления доступны Tab/Enter, ошибки связаны с полями; `viewport` присутствует на всех страницах. |

Значения enum в БД, формах и URL сохраняются. Меняются только отображаемые подписи и классы значков:

| Значение | Подпись | Визуальный тон |
|---|---|---|
| Request NEW | New | secondary |
| ASSIGNED | Assigned | primary |
| IN_PROGRESS | In progress | warning с тёмным текстом |
| COMPLETED | Awaiting review | info с тёмным текстом |
| CLOSED | Closed | success |
| CANCELLED | Cancelled | secondary, outline |
| Equipment OPERATIONAL | Operational | success |
| UNDER_REPAIR | Under repair | warning с тёмным текстом |
| OUT_OF_SERVICE | Out of service | danger |
| DECOMMISSIONED | Decommissioned | secondary |
| Priority LOW | Low | secondary |
| MEDIUM | Medium | primary, спокойный |
| HIGH | High | warning с тёмным текстом |
| CRITICAL | Critical | danger |
| User active / inactive | Active / Inactive | success / secondary |

`COMPLETED` нигде не подписывается как окончательно закрытый ремонт. Enum-код можно сохранить в `data-status`/`data-priority` для диагностики и проверок, но человек видит понятную подпись. Палитра уточняется CSS в пределах этого направления; соответствие текстов и состояний фиксировано.

Минимальные общие фрагменты: `fragments/head.html` (title, viewport, CSS), `navigation.html` (активный раздел и разрешённые ссылки), `messages.html` (flash), `badges.html` (статусы/приоритеты/активность), `time.html` (единое время). Они подключаются обычными `th:replace`; для содержимого страниц остаются явные шаблоны. Фрагмент `maintenance/history` переиспользуется, а не копируется. Ошибки полей оформляются общими CSS-классами; мелкие обёртки не превращаются в отдельную систему компонентов.

## 6. Техническое решение

Сохраняем Java 21, Spring Boot 4.1.0, PostgreSQL 18, Flyway, JPA и существующий Maven-стек. Bootstrap 5 уже выбран в 04. На этапе оформления добавляются локальная CSS-копия конкретной зафиксированной версии Bootstrap 5 с лицензией и указанием версии, а также `static/css/app.css`. Версию и происхождение файла фиксирует патч каркаса; `latest` и CDN не используются. Для переносимой навигации Bootstrap JS, иконки и web fonts не требуются. Новых Maven/Node-зависимостей, layout dialect и Thymeleaf Security extras нет.

Для оформления входа требуется узкое разрешение `GET /css/**` до `.anyRequest().authenticated()`. Оно открывает только ресурсы CSS; не отключает security chain/CSRF и не меняет защиту бизнес-маршрутов. Это необходимая часть доставки оформления, не общий пересмотр безопасности этапа 13.

| Компонент | Ответственность |
|---|---|
| Существующий `HomeController` | Получает `CustomUserDetails`, вызывает сервис, передаёт готовый Dashboard DTO в `home`. Не обращается к Repository. |
| Новый `dashboard/DashboardService` и `dashboard/dto` | Проверка актуального пользователя, выбор контракта по роли, загрузка чисел и ограниченных списков, подготовка DTO. Это прикладной экран, не новая доменная сущность. |
| `UserService`, небольшой метод чтения `CurrentUserSummary` | Возвращает `Optional` с `id`, `fullName`, `role` активного пользователя по доверенному ID. Нужен Dashboard и общей навигации; не используем `getAllUsers()` и не передаём `User`/хеш пароля в модель. Dashboard отклоняет отсутствие активного summary. Отдельный сервис для текущего пользователя не нужен. |
| Общий `common/controller/NavigationAdvice` | Готовит отдельный атрибут меню для существующих защищённых контроллеров, используя summary и серверную аутентификацию. Привилегированные ссылки показываются только при совпадении актуальной роли и роли сессии. При отсутствии активного summary или устаревшей роли остаются нейтральные переходы и выход; сам provider меню не добавляет отказов к существующим операциям. Login/access-denied не зависят от этого чтения. Не перезаписывает предметные `canManageEquipment` и флаги действий заявки. |
| `RepairRequestRepository` | COUNT по явным предикатам §3 и SELECT с пределом 5. Ограничение автора/назначенного техника и статуса выполняется в запросе до лимита. |
| Thymeleaf/CSS | Отображение готовых данных и меню. Не вычисляет права из параметров URL и не фильтрует загруженные чужие записи. |

Не загружаем все заявки через `findAll`, `findVisible` или `getListPage` ради `size()` и `stream().limit(5)`: они не нужны для счётчиков и ограниченного предпросмотра. Для четырёх ADMIN-статусов достаточны простые COUNT; для critical — COUNT с приоритетом и набором четырёх статусов; для техника — COUNT по назначению и одному статусу. SELECT возвращает `List`, использует фиксированный `PageRequest.of(0, 5)` внутри сервиса, без возвращаемого `Page`, дополнительных count-запросов и пользовательских `page/size`. Этот SQL-предел — ограничение предпросмотра, а не пагинация полных списков этапа 12.

В предпросмотре загружаются необходимые связи to-one либо DTO-проекция, без N+1. Разрешения выводятся из сервиса, не из аргументов запроса. Одна read-only транзакция `REPEATABLE_READ` охватывает проверку пользователя, счётчики и списки Dashboard: изменение статуса между SELECT не должно давать противоречивую сводку. Это тот же обоснованный подход, который уже применён в `EquipmentDetailsService`. Блокировки записи и кеш не нужны. `spring.jpa.open-in-view=false` сохраняется.

Схема БД и миграции V1–V5 не меняются. Индексы, generic repositories, базовые контроллеры, универсальные permission engines и массовый рефакторинг существующих сервисов для этой задачи не требуются. Достаточность запросов проверяется на PostgreSQL, не оценивается по одному внешнему виду страницы.

Каждый шаг поставляется отдельным проверяемым патчем с полным базовым коммитом и своими командами проверки. При необходимости большой шаг делится на меньшие без изменения границ. Для коммита добавляются только явно перечисленные файлы; перед коммитом — `git diff --cached --check`, после — проверка статуса. Отправку в GitHub выполняет разработчик после успешной проверки и коммита. До получения результатов шага 1 реализацию не начинаем.

Этап 11 принимается после фактического выполнения контрактов трёх ролей, общего оформления перечисленных страниц, успешного полного прогона и ручной проверки. Документационный патч сам по себе этап не завершает.
